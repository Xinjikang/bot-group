# 项目文档与测试报告

## 目录与版本管理

项目文档在成员当前工作区维护，随分支提交、审查和合并。软件项目使用以下分类：

| 位置 | 内容 | Git |
| --- | --- | --- |
| `docs/requirements/` | 需求、范围、验收标准与开发计划 | 纳入 |
| `docs/design/` | 方案、设计、讨论结论与取舍依据 | 纳入 |
| `docs/ui-spec/` | UI 视觉、组件状态及响应规则，入口 `UI-SPEC.md` | 纳入 |
| `docs/engineering/` | 已实现的架构、接口、技术契约与维护知识 | 纳入 |
| `docs/guides/` | 安装、使用、发布与协作指南 | 纳入 |
| `scripts/` | 可复用测试及 `TEST_INDEX.md` 用例索引 | 纳入 |
| 项目主目录 `reports/tests/` | 测试结果、日志、截图、现场证据及执行产物 | 忽略 |
| 项目主目录 `reports/research/` | 技术调研、选型对比及可行性实验 | 忽略 |

文档入口为 `docs/INDEX.md`。审查、返修与验收结论写入任务节点，长期有效的结论同步到相应文档。测试索引记录用例用途、运行条件与命令；执行结果放入测试报告。

技术文档直接说明需求、方案、技术依据、行为、约束和操作步骤。使用职责称谓、通用路径及示例数据；真实环境信息保留在测试报告。代码注释、docstring 和工具说明解释代码行为、技术原因、边界及兼容性依据。

## 工作区与交接

shared 成员在主目录维护文档，worktree 成员在已分配工作区维护文档。上游在交接前提交需求或设计，记录文档路径、提交及任务节点；下游按项目约定同步相应基线。

所有成员使用引擎注入的“项目主目录”绝对路径拼接 `reports/` 作为报告位置。测试使用 `tests/<版本>/<日期>-req-<ID>/REPORT.md`，技术调研使用 `research/<专题>/`，相邻 `evidence/` 保存证据。写入前以 `git check-ignore` 核验忽略规则，报告由维护者单独备份。正式采纳的方案整理到 `docs/design/`，已实现的技术契约整理到 `docs/engineering/`。

目录调整保持项目现有角色、交接顺序、审查返修与关闭权限，具体以项目 AGENTS.md 为准。软件模板的独立版本测试由用户发起。

## 模板、初始化与授权

软件模板 1.5.1 生成上述分类目录与 `reports/.gitignore`，包含 `docs/ui-spec/UI-SPEC.md` 默认基线。前端维护项目采用的规范，审查员检查一致性。导入补充保留同路径已有规范，已有 `doc/` 项目生成 `doc/ui-spec/UI-SPEC.md`；已登记项目按需手动补充文档。新建项目根 `.gitignore` 同时忽略 `/reports/`，初始化提交排除该目录，显式选择其中的文件会被拒绝。

模板路径校验允许 `reports/.gitignore`；为恢复既有初始化快照继续识别旧 `internal/.gitignore`。导入预览保留项目已有文件及忽略规则，迁移既有文档需要单独执行。其他项目模板按各自用途组织成果，已有 `doc/` 项目仍可复用原目录。

Hermes 与 Codex 的 work/chat 提示词注入当前工作目录、项目主目录、目录模式及工作区资源。文档分类、报告位置、Git 策略和交付要求由项目 `AGENTS.md` 管理；软件项目据此将报告写入主目录 `reports/`。已登记项目若仍引用旧“报告目录”字段，应将规则更新为使用“项目主目录”拼接 `reports/`。

Codex 在明确入组、创建工作区或保存目录配置时，授权已分配工作区；共享报告目录位于工作区之外时，额外授权主目录 `reports/`。普通启动与会话恢复沿用已有权限。既有 worktree 成员应通过成员与目录配置更新报告目录授权，详见 [Codex 目录授权](CODEX-PROFILE-HOMES.md)。

## 既有资料整理与发布

旧 `internal/` 资料按内容归入需求、设计、工程、指南或测试报告。旧快照与当前文档比较，以最新有效内容为准，清理过时副本；有效的独有内容归入对应专题。迁移记录保存旧路径与新位置映射，便于从既有任务交接记录定位资料。

源码归档包含 `docs/`，测试报告与现场证据由发布白名单排除。发布前核对跟踪文件和归档清单，详见 [发布指南](RELEASE-GUIDE.md)。公开仓库的需求与设计采用可公开的技术表述。
