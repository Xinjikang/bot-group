# Windows 进程探测兼容性

## 问题与目标

Hermes 唤醒前通过进程查询防止同会话重复执行。WMIC 缺失时，查询返回未知，队列保留 queued 并等待后续探测。Codex 重启恢复查询及 MCP 父进程身份解析也存在同一依赖。

目标是让全新 Windows 11 通过项目依赖安装即可完成进程探测，同时保留查询失败时的并发保护。

## 方案

引擎和 MCP 共用 `engine/process_query.py`。Windows 枚举复用项目已有 Toolhelp 原生快照，先按名称筛选候选；psutil 读取候选的当前名称及参数列表。每轮创建新的候选进程对象，避免沿用 PID 复用前的名称缓存，同时控制全系统扫描开销。项目依赖、发布锁文件和安装自检统一包含 psutil。

采用参数列表进行 profile 和会话匹配，保留 Unicode、空格及参数边界。Codex 持久化 PID 通过内联 MCP 配置中的执行上下文核验归属。

PowerShell/CIM 可提供系统进程查询能力，但每次调用会启动解释器并序列化输出；常驻队列的高频查询采用进程内库。现有 Windows 原生进程树终止实现继续负责停止操作。

## 失败边界

查询结果保留存在、缺席、未知三态。相关进程的参数读取失败会使本轮查询返回未知；已确认无关的进程只读取名称。枚举期间正常退出的进程可跳过。已确认退出或 PID 复用的进程按缺席处理。

错误日志按调用范围和阶段限频，并在查询恢复后记录恢复事件。日志包含异常类型和错误码，省略命令行及异常正文。
