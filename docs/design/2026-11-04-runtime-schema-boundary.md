# 数据库初始化与运行流量

## 问题与目标

HTTP 连接工厂、MCP 操作回执、任务池和后台循环曾调用完整数据库初始化。初始化包含迁移写入及索引替换，使读取请求参与 SQLite 写锁竞争，忙碌时可能等待 busy_timeout 或返回锁超时错误。

目标是让用户消息在 Bot 执行期间正常入库，让 WAL 模式的页面读取在业务写事务持锁时继续读取已提交快照。消息路由、发言位、授权和 MCP 回执的原子性保持现有契约。

## 初始化边界

- 引擎生命周期在启动后台线程及接收请求前执行 `db.init_schema`，失败终止启动。
- 独立升级验证工具、测试夹具在运行业务前显式初始化目标数据库。
- HTTP、MCP、任务池、队列、扫描、心跳退出及停止处理使用已初始化的数据库；连接获取只设置连接级 PRAGMA。
- 同一进程打开另一数据库时，由该数据库的独立入口负责初始化；省略全局缓存，避免文件替换或测试数据库切换造成误判。

## 索引升级

`hermes_execution_active` 的目标定义为 session 上的部分唯一索引，条件为 `state != 'terminal'`。定义兼容时保持 schema_version。旧定义的 DROP 与 CREATE 在同一 savepoint 中执行，失败回滚并保留外层事务；异常由启动调用者处理。

## 验证与生效

隔离数据库覆盖旧库升级、数据保留、重复初始化、索引替换失败回滚。HTTP 回归覆盖另一连接持写锁时读取已提交数据、Bot 持续忙碌时连续消息和并发轮询、MCP 写入与重放。运行路径通过 SQLite authorizer 禁止 DDL，后台循环验证同一约束。测试入口见 `scripts/TEST_INDEX.md`。

引擎代码更新后由管理员手动重启，启动时完成数据库准备。现场两次发送延迟与具体锁持有者的对应关系需结合后续运行观察确认；隔离回归验证上述确定的迁移竞争缺陷。
