# 消息发送延迟与可观测性

## 现状与测量

普通用户消息经 HTTP 校验、SQLite 消息与 inbox 写入、唤醒入队后返回。该路径仅将工作登记到队列，运行时连接由队列消费者处理。

隔离生产数据库副本、关闭消费者、每次清空唤醒队列后，40 次发送中位数约 9 ms，P95 约 86 ms，最大约 97 ms。逐阶段记录显示，较慢样本主要耗在 SQLite COMMIT（约 79～90 ms）。原实现先提交消息与 inbox，再为唤醒作业提交第二次事务。真实浏览器合成数据中，100 条消息重绘约 8～12 ms，1000 条约 75～83 ms。原始现场请求缺少耗时记录，以上数据用于确认可复现的延迟来源，现场整体耗时仍需阶段日志核验。

交错运行原路由与统一提交后的路由各 40 次，原路由中位数约 9.0 ms、P95 约 86.8 ms；新路由中位数约 6.4 ms、P95 约 77.4 ms。提交次数由每次两次降为一次，偶发磁盘提交尖峰仍然存在。该实验评估后端路由与 HTTP 测试客户端，生产页面的网络、事件传递和重绘需结合现场继续核验。

## 实现契约

- 消息、inbox、话题状态与该消息的唤醒入队共享一次事务；全部完成后提交。保留队列去重、成员与项目就绪校验、话题 DFS 顺序及既有 SQLite 持久性设置。
- HTTP 普通消息路径记录连接、路由、事件发布、总耗时、结果及持久化消息 ID。路由记录写锁取得、消息处理、入队和提交耗时。日志仅记录结构化标识与耗时，省略正文、凭据和异常原文。
- 主输入框在本目标正在发送时显示“发送中…”、禁用发送按钮并设置忙碌状态。成功后按现有目标和文本一致性条件清空输入；失败保留原草稿。切项目、切话题后按当前目标恢复状态。
- 消息上屏继续采用服务器确认与 SSE，同一目标的重复提交继续由发送门禁阻止。

## 验证与生效

隔离 SQLite 回归验证单次提交、提交前对其他连接不可见、异常回滚和入队去重；复用消息路由、话题顺序、MCP 幂等和运行流量边界回归。浏览器采用全拦截的合成 HTTP，验证延迟响应时的即时状态、成功、失败、切换目标及深浅主题和窄屏。性能对照使用相同的只读快照与临时副本，禁止启动生产消费者或发送生产消息。

测试证据写入项目主目录的忽略目录。引擎修改在管理员手动重启后生效，前端修改刷新页面后生效。
