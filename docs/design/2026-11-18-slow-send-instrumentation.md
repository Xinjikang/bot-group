# 慢发送引擎内分步计时方案

日期：2026-11-18
状态：设计定稿，待拆解
关联现场：11542（11-12）、11670（11-17）、11835（11-18，已由探针捕获）

## 1. 目标

三次现场确认发送路径存在瞬时停顿（11835：lock 2170.4ms + prepare 6530.3ms + 事务外段 2344.7ms）。现有持久化计时只有 connect/lock/prepare/commit 四段总数，无法落点到具体步骤，也无法识别写锁持有者。本方案给引擎加两处诊断埋点：

1. **发送分步计时**：route 路径各步骤的墙钟与线程 CPU 时间成对记录。
2. **写事务起止记录**：每个写事务的开始/结束/连接标识/线程标识，用于识别锁持有者与持锁时长。

## 2. 依据

- 11835 重放（E 盘隔离库 + 现场规模 2 条消息 + 双连接持锁 2.170s）：等待方取锁 2.176-2.280s 可复现，锁后 prepare 仅毫秒级——**锁竞争最多解释 lock 段，prepare 6.53s 另有来源**，且现场持锁者自身就是异常（正常持久化毫秒级）。必须拿到语句级落点才能区分语句级停顿与进程级停顿。
- 内存库重放：现场规模下 SQL 总量十几条、计算毫秒级——计算型假设基本排除，prepare 停顿为等待类，落点只能靠语句级计时。
- 探针现有能力边界：磁盘/进程采样只能给关联线索，无法归属请求与事务。

## 3. 埋点设计

### 3.0 修复候选一：messages 索引（先于埋点验证）

bot-36 已定位首个可修缺陷并经隔离对照实验证实（REMEDIATION-11835.md），reviewer-02 独立核验确认全表扫描共**四处**、均持写锁执行：`_round_spoken`（router.py:294，thread_id+sender+round+parent_id IS NULL）、当轮用户消息（router.py:421，thread_id+sender='user'+round）、`_edge_responded`（router.py:304，parent_id+sender）、DFS 接话查询（router.py:368，parent_id+sender）。生产库 messages 无任何索引（index_list 为空）。9841 行合成库对照：prepare 中位 10.774ms → 加 messages(thread_id,sender,round,parent_id) 复合索引 0.788ms → 撤索引回 10.049ms。现场 6.53s 不能全归它，但它是第一项可修的持锁开销。消息表只增不改，写成本可忽略（reviewer-02 核验）。

验证项（隔离库，用新连接复核执行计划后再定采用哪些索引）：
- 复合索引 messages(thread_id,sender,round,parent_id) 服务 router.py:294 与 :421 两处；`:304` 与 `:368` 以 parent_id 为首列，该复合索引无法服务，父消息查询单独评估对应索引（如 messages(parent_id,sender)）的收益。
- 旧库升级路径：生产库已有数据，CREATE INDEX 的耗时、事务方式与备份回退步骤。
- 写入成本与分发一致性：消息表只增不改，写成本预期可忽略（仍按对照实测确认）；覆盖有无现成发言位、话题与点对点发送四类。
- 顺序：索引验证与埋点验证并行，各自独立交付。

### 3.1 发送分步计时（engine/api.py + engine/router.py）

计时点按代码实际顺序（router.py route_message，BEGIN IMMEDIATE 位于 637 行）：

| 组 | 位置 | 内容 |
| --- | --- | --- |
| C1 | db.get_connection 内 | 配置读取（.env） |
| C2 | db.get_connection 内 | 目录访问 |
| C3 | db.get_connection 内 | sqlite3.connect 打开 |
| C4 | db.get_connection 内 | 两条 PRAGMA |
| S1 | api.py 取得连接后 | threads 项目查询（api.py:322） |
| S2 | route_message 前 | is_builtin_user + commands.dispatch 判断（api.py:328-329） |
| S3 | BEGIN IMMEDIATE | 写锁获取（与现有 lock_ms 同源） |
| S4 | 事务内前半 | 话题行读取、成员名单（两处调用）、提及校验、发言位查询、父消息查询 |
| S5 | 事务内中段 | 消息插入、执行记录、收件箱分发、活跃时间更新 |
| S6 | 事务内后段 | 下一发言者树计算（按话题消息量递归）、发言位更新、唤醒入队 |
| S7 | COMMIT | 提交（与现有 commit_ms 同源） |

每组记录成对值：`wall_ms`（单调时钟差）+ `thread_cpu_ms`（同线程 CPU 时钟差）。墙钟长而线程 CPU 短=等待型，反之为计算型——这是区分两类停顿的直接证据。

### 3.2 写事务起止记录（engine/db.py 或 router.py 事务包装处）

每个写事务在 BEGIN IMMEDIATE 与 COMMIT/ROLLBACK 处各记一行：`conn_id`（连接对象 id）、`thread_id`、`wall_ts`、`is_begin/is_end`。正常持久化毫秒级，日志量小（每秒个位数行）。现场 2.17s 锁等待的持有者即可由同窗口的 begin 行识别，持锁时长由成对行差值直接得出，不依赖等待方倒推。

### 3.3 输出与控制

- 输出：独立 jsonl 文件（如 `logs/slow-send-diag.jsonl`，随引擎日志目录），字段固定、机器可解析；按天轮转，容量上限后保留最近。
- 开关：环境变量 `XDG_SLOW_SEND_DIAG=1` 时启用（引擎自身读环境，不设=零开销零日志）；引擎由网关 spawn 子进程的跨进程变量只透传 XDG_ 前缀，沿用该约定。
- 开销目标：单点 <0.5ms（time.monotonic + time.thread_time 各一次调用）。

## 4. 验证（隔离环境，不碰生产）

1. 双连接重放：持锁方注入 2.17s 暂停，核对 S3 墙钟≈2.17s、线程 CPU≈0，begin/end 行正确识别持有者。
2. 人为慢注入 prepare 段（S5/S6 各一次），核对落点精确到组。
3. 开销实测：1000 次正常发送，开关前后 p50/p99 对比，日志体积统计。
4. 回归：scripts/TEST_INDEX.md 既有引擎用例全绿。

## 5. 部署与验收

生产引擎代码修改 + 重启。**重启时间由主人定**；重启后 `XDG_SLOW_SEND_DIAG=1` 常开至下一次现场捕获，捕获后由主人决定关停。索引上线前明列迁移、备份、回退步骤与预计中断时间，由主人确定上线时点。

验收交付（按 bot-36 2026-11-18 口径）：
1. 性能补丁（索引）——隔离库对照数据 + 旧库升级路径验证。
2. 受控复现——双连接稳定复现锁等待；连接段与锁后操作分别注入可辨认延迟，核对诊断指向实际步骤；诊断交付只验收观测能力，自然复现的慢路径用相同输入验证针对性修复。
3. 上线后实际发送数据——沿用原阈值（连接 5s/路由 3s/总计 5s），建议连续七个实际使用日观察窗口，覆盖隔夜首发与白天发送；报告首发样本数、总发送数、耗时分布与异常；同类卡顿沿慢步骤继续修，样本不足标记待验。

## 6. 边界

- 不承诺识别锁持有者所属请求的业务内容，仅起止时间 + 连接/线程标识（进一步业务关联是后续可选项）。
- 分步计时本身不改任何业务逻辑，纯旁路记录。
- 探针侧增强（1s 磁盘环形缓冲）是独立层，不冲突、可并行。
