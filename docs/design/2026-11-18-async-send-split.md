# 发送路径异步拆分评估（候选方案）

日期：2026-11-18
状态：评估稿，待讨论定案后实施
来源：主人 11916 质疑「写消息与唤醒是否必须同一把锁」→ bot-36 11921 提出拆分方案 → 架构师评估

## 1. 现状

route_message 在 BEGIN IMMEDIATE 一个写事务内完成：消息插入、收件箱分发、下一位发言者判定（含树计算）、发言位更新、唤醒登记（wake_runs）、提交。事务设计的原始动机是崩溃一致性：引擎中途死亡时，已发消息不会处于「没人接着处理」的状态。代价：判定与树计算的毫秒~秒级工作量全部压在持锁段，发送回执被拖长；索引缺失时（#314 已定位六处全扫）放大到秒级。

## 2. 拆分方案（bot-36 提议）

- **发送事务（短）**：必要校验 + 消息插入 + 「本话题待调度」记录，一事务提交，立即回消息编号，页面显示已发送。
- **后台处理**：按同一话题的消息 id 顺序，选下一位发言者、登记唤醒。
- **崩溃恢复**：重启后从「待调度」记录续处理；重复执行不得多唤醒。

## 3. 评估结论：可行，方向正确，但有四条硬约束

### 3.0 归属边界（reviewer-02 四缺口补齐，2026-11-18）

- **收件箱分发**：留在发送短事务内。收件人=话题成员，有界（通常 4-6 行插入），成本毫秒级；与消息同事务保持「消息可见=收件箱可见」的一致性。
- **收口关闭判定**：归后台处理。settle_thread（router.py:378-389）含 `UPDATE inbox SET status='expired' WHERE ... message_id IN (SELECT id FROM messages WHERE thread_id=?)` 子查询扫描与 wake_jobs 批量更新，不能留在发送短事务；移入后台 worker，与选人/登记同批处理。
- **点对点路径**：保持现状（不拆）。点对点消息（thread_id IS NULL）无轮次/树计算，路径本就短；拆分范围只覆盖话题发送。
- **与既有扫描器兜底的关系**：拆分新增的「选人+登记」后台 worker 是 wake_jobs 的**生产者**；既有 wake 投递 worker（delivery.py）是**消费者**——生产-消费分工，互不重叠、各自幂等。重启恢复沿用 db.py 现有机制（wake_jobs running→queued 重发信号），补上「待调度记录」的重启扫描即可，不引入第二套兜底扫描器。

### 3.1 短写事务是拆分成败的唯一关键

SQLite 同一时刻仍只有一个写者。若后台把「选人计算」放在自己的写事务里慢慢做，下一条发送照样等它的锁——拆分等于没拆，只是把等待从「同一请求内」挪到「下一条请求」。**硬约束：后台的读与计算必须全部在写锁外完成（WAL 快照读），写锁只在提交「发言位更新+唤醒登记+待调度消费标记」的毫秒级事务内持有。** 这是 5 秒慢后台测试能否通过的判定点。

### 3.2 每话题严格按消息 id 顺序处理

两个并发到达的消息若被两个处理者同时计算，会基于同一旧状态各自推进发言位 → 乱序/重复唤醒。硬约束：单处理者按 topic 串行（v1 用单 worker 全库串行最简单），或按话题 claim 后独占处理，二者取一。处理者崩溃后其 claim 要能被回收重领（租约超时）。

### 3.3 崩溃一致性与幂等

- 消息 + 待调度记录同一事务提交 → 「消息已接受、待调度」原子持久化，重启必被处理。
- 处理事务 = 消费待调度记录 + 写发言位 + 登记唤醒，同一事务 → 任何时刻死亡都不会出现「消费了但没唤醒」或「唤醒了但标记还在」。重放=整事务重做，幂等由事务边界保证，不需额外去重逻辑。
- wake_runs 既有队列表可复用；唤醒投递幂等沿用现有机制。

### 3.4 发送回执与业务语义

发送提交即回执（消息编号），页面立即可发下一条；bot 的响应时间由后台处理节奏决定，对用户不可见。**代价**：消息「已发送」到「唤醒入队」之间多了一个后台窗口（正常毫秒~秒级），若后台积压，bot 响应会滞后——需要在积压监控上给出可观测性（待调度队列深度）。

### 3.5 顺序与复核规则（bot-36 提议，2026-11-18）

- **只看截至第 N 条**：后台处理第 N 条消息时，历史与树计算只取 id≤N 的消息，后到的消息不参与本次判定。
- **提交前复核**：提交选人结果前，重新核对当前发言位、话题是否已关闭、待调度记录是否已被处理——任一状态变化则放弃本次结果重新判定。连发、话题关闭、重启并发三种情形下保证顺序且不重复登记。
- 已关闭话题在发送入口仍须拦截（现状行为保留）。

## 4. 验证场景（对应 bot-36 要求）

1. **连发两条**：后台故意慢 5 秒时，用户连发两条消息，两条发送回执都必须毫秒级返回（判定后台读计算确实在锁外）；**加锁持有断言：后台占写锁的时间必须保持毫秒级（采样后台写事务 wall 耗时），且两条发送的耗时与后台慢度无关**。记录两次实际耗时，随后检查按序调度。
2. **两条之间重启**：保存后重启——已确认的消息都在、待调度续处理；调度中重启——恰好唤醒一次、不重复。
3. **乱序**：A 处理中 B 到达 → B 的处理严格排在 A 之后（同一话题顺序不颠倒）；复核规则触发时放弃重判。
4. **回归**：既有 103 项隔离测试全绿；话题与点对点分发、发言位流转与现状一致；点对点路径不拆、行为不变。

## 5. 与 #314 的关系

- #314（双索引 + 分步计时）继续推进，与拆分互不阻塞：索引让锁内工作变快，无论拆不拆都有收益；分步计时数据用于确认 6.53s 大头，也用于拆分后验证后台占锁时间。
- 拆分是独立需求（引擎并发模型改造 + 迁移 + 回归），按 AGENTS.md 生产变更流程单独立项，方案定案与上线时点由主人决定。
- 风险提示：拆分不解决「后台本身被环境拖慢」（若 E 盘整体瞬时劣化，后台读计算同样会慢），但慢点从发送主路径移出，用户可继续发送；秒级根因仍靠 #314 计时与探针追查。
