## 1. 现状（2b27037 后）

route_message 在 BEGIN IMMEDIATE 一个写事务内完成：消息插入、收件箱分发、下一位发言者判定（含树计算）、发言位更新、唤醒登记（wake.enqueue commit=False）、一次提交。选人扫描的耗时全部压在发送请求的持锁段内，回执被拖长。#314 已定位六处全扫查询点；11-18 09:14 现场分段计时：写锁内准备阶段 6.53s、登记+最终提交合计约 0.12s，逐条查询计时尚未做。

## 2. 方案（bot-36 12047 修订，主人 12035 体验要求）

- **发送事务**：必要校验 + 消息插入 + 收件箱分发 + 话题状态更新（上屏相关字段），提交后**立即回执**——页面显示「已发送」，消息上屏，可接着发下一条。
- **后台处理**：按同一话题的消息 id 升序逐条补做：选下一位发言者（树计算，锁外读）→ 发言位更新 + 唤醒登记 → 推进该话题游标。
- **顺序约束**：消息与收件箱同次提交先可见，后台选人/唤醒在其后——成员被唤醒时消息必已在收件箱可读（reviewer-02 顺序要求天然满足）。
- **崩溃恢复**：后台游标持久化（存储位置由实现定），重启后从游标续处理未办消息；重复执行不得多唤醒（wake_jobs 去重沿用现有机制）。
- **改动范围**：发送事务只留「上屏必需」的写入；选人扫描与唤醒登记移出发送请求。收口判定与点对点路径本次不拆（保持现状，低频/路径短）。

## 3. 边界与风险

- **选人扫描移出写锁**：秒级准备阶段工作从发送请求移出，发送回执只等「消息+收件箱」提交。后台读与计算在写锁外完成（WAL 快照读），写锁只在「发言位更新+唤醒登记+游标推进」的毫秒级事务内持有——这是 5 秒慢后台测试能否通过的判定点。
- **后台按话题串行**：两个并发到达的消息若被两个处理者同时计算，会基于同一旧状态各自推进发言位 → 乱序/重复唤醒。硬约束：单处理者按 topic 串行（v1 用单 worker 全库串行最简单），或按话题 claim 后独占处理，二者取一；处理者崩溃后 claim 可回收重领（租约超时）。
- **与既有 scanner 的职责边界（实现设计硬要求）**：既有周期扫描器（scanner.py 来源1，154-166 行）在话题发言位为空时兜底调用 _next_speaker 重算选人并写发言位——与新后台 worker 的「按游标选人+写发言位」职责重叠，两套并存会互扰发言位（重复选人/乱序）。实现设计必须**收窄或废除**该兜底分支：话题选人与唤醒统一收归新后台 worker（游标续办已覆盖重启与漏办情形），scanner 保留点对点唤醒、任务池、静默超时收口、全员弃权收口、需求拆解职责；具体收窄方式在实现设计阶段定，边界必须唯一。
- **处理事务与幂等**：后台处理事务 = 写发言位 + 登记唤醒 + 推进游标，同一事务 → 任何时刻死亡都不会出现「唤醒了但游标没推进」或「游标推进了但没唤醒」。重放=整事务重做，幂等由事务边界保证。
- **发送回执与业务语义**：发送提交即回执，页面立即可发下一条；bot 的响应时间由后台处理节奏决定，对用户不可见。代价：消息「已发送」到「唤醒入队」之间多了一个后台窗口（正常毫秒~秒级），后台积压时 bot 响应滞后——需要可观测性（每话题游标落后最新消息 id 的深度）。
- **收口路径**：本次不拆，保持现状行为（低频路径）。
- **点对点路径**：本次不拆，保持现状行为（无轮次/树计算，路径本就短）。
- **速度预期**：秒级卡点大头在选人扫描段，本方案将其移出发送请求；实际改善幅度按验收场景实测，不预设结论。

## 4. 验证场景

1. **选人停 5 秒连发两条**：故意让后台选人停 5 秒，期间用户连发两条消息——两条发送回执都必须毫秒级返回，且两条在后台恢复前按序上屏、显示「已发送」；**加锁持有断言：后台占写锁的时间必须保持毫秒级（采样后台写事务 wall 耗时），且两条发送的耗时与后台慢度无关**。
2. **重启续办**：保存后重启——已确认的消息都在、后台从游标续处理；调度中重启——恰好唤醒一次、不重复。
3. **乱序**：A 处理中 B 到达 → B 的处理严格排在 A 之后（同一话题顺序不颠倒）。
4. **回归**：既有 103 项隔离测试全绿；话题与点对点分发、发言位流转、唤醒去重与现状一致；点对点与收口路径不拆、行为不变。
