## 1. 现状（2b27037 后）

route_message 在 BEGIN IMMEDIATE 一个写事务内完成：消息插入、收件箱分发、下一位发言者判定（含树计算）、发言位更新、唤醒登记（wake.enqueue commit=False）、一次提交。判定与树计算的耗时全部压在持锁段。#314 已定位六处全扫查询点；11-18 09:14 现场分段计时：写锁内准备阶段 6.53s、登记+最终提交合计约 0.12s，逐条查询计时尚未做。

## 2. 方案（主人 11999 定案方向）

恢复 2b27037 之前的事务边界：

- **第一段事务**：必要校验 + 消息插入 + 收件箱分发 + 话题状态更新 + 选人计算 + 发言位更新，提交。
- **第二段事务**：唤醒登记（wake.enqueue 恢复默认提交行为），单独提交。
- **接口回执**：与旧版一致——接口在唤醒登记完成后返回，页面显示新消息的时机不变。
- **改动范围**：仅 router.route_message 的事务边界。不引入游标、不移动收件箱分发、不新增后台 worker、不拆发送。

## 3. 边界与风险

- **选人树计算仍在第一段写锁内**：恢复后，选人计算依旧发生在发送请求的持锁段内（旧版即是如此），回退不改变其执行位置。#314 已定位六处全扫查询点，其耗时占比待逐条计时确认；回退消除的是「唤醒登记与消息共用一次提交」的耦合，提交次数从一次回到两次。
- **两段提交之间的崩溃窗口**：第一段提交成功后、唤醒登记前崩溃 → 消息+收件箱已持久、唤醒未登记。此时 wake_jobs 尚无该消息的登记记录，既有 running→queued 重发机制不覆盖；是否存在从消息/收件箱数据重建唤醒的补登路径，未经验证——如实注明，不预设兜底。该窗口是 2b27037 之前的既有行为。
- **唤醒登记独立提交失败**：消息已可见、唤醒未登记，行为与旧版一致。
- **点对点路径**：点对点（thread_id IS NULL）与话题共用同一事务边界——第一段提交（消息+被 @ 者 inbox 行）与第二段唤醒登记循环（多收件人按次入队）均为共用代码；回退对点对点同样生效，提交次数同样从一次回到两次，其余行为不变。
- **速度预期**：恢复两段提交能否改善实际发送耗时，现有计时不足以断言（11-18 09:14 的 11.4s 卡点中，写锁内准备阶段 6.53s、登记+最终提交合计约 0.12s）。必须同一数据对照测。

## 4. 验证场景

1. **对照测速**：恢复前后用同一数据（含 #314 已知慢场景）各测多轮发送，对比耗时分布——基线为当前实现（一次提交），对照为恢复后（两段提交）。
2. **回归**：既有 103 项隔离测试全绿；话题与点对点分发、发言位流转、唤醒去重与现状一致；点对点路径行为不变。
3. **崩溃窗口（如可行）**：第一段提交后、唤醒登记前中断，重启后消息可读、唤醒由既有兜底机制处理——不丢消息、不多唤醒。
