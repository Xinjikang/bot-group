# 项目配置与工作目录管理

项目配置、目录和规则同步入口见下文，全局架构见 [工程说明](ENGINEERING.md)。

## 项目身份与入口

项目保留稳定 ID 和可编辑的显示名。旧项目的当前 `projects.name` 固定为 ID，新增 `display_name` 初始沿用该值。接口列表同时返回 `id`（等于兼容字段 `name`）；任务、消息、成员启停和会话继续使用稳定 ID。改显示名只更新项目展示字段，旧接口 `new_name` 也按显示名处理。

点击项目标签打开项目配置：基本信息、AGENTS.md、成员与目录。顶部“成员”按钮已移除，成员启停和 profile 编辑统一从项目配置的“成员与目录”进入。

新建和导入项目使用共用七步向导，配置项目、协作方式、角色、规则、成员与工作区资源后确认提交；引擎生成 `p_` 加 UUID 的稳定 ID，保存后界面只读展示。旧调用方显式传入 `name` 的兼容行为保留。成员目录模式采用金色选中态的双选项单选控件，支持键盘操作。详见 [项目向导](PROJECT-SETUP-WIZARD-2026-10-14.md)。

AGENTS.md 读取成功后显示“已加载”；文件不存在时提示保存后创建，读取错误继续显示具体原因。隔离浏览器回归覆盖正文与加载完成状态，防止正文已显示仍停留在“加载中”。

成员列表使用紧凑卡片：顶部展示姓名、profile、启停状态和操作，下方展示目录与校验状态；“工作区”按钮与“编辑”并排，打开独立弹窗。配色沿用深蓝与金色，窄屏允许顶部操作换行。
profile 紧跟姓名，“已启用”以绿色标记；“目录可用”与路径同行右对齐，长路径在窄屏省略展示。

成员编辑支持 Hermes/Codex，描述、SOUL/AGENTS 与环境配置按宿主能力写入全局 profile。模型、供应商及推理强度默认保存项目覆盖；“应用到全局”写入全局并清空当前项目对应覆盖，其他项目保持原配置。模型及供应商决定实际支持范围，Hermes 已有 `reasoning_overrides` 优先级保持。保存沿用 revision 冲突检测和备份机制，详见 [统一模型编辑](UNIFIED-MODEL-EDITOR.md)。

## 项目角色与加入成员（2026-09-30）

Bot 保存全局宿主类型、物理 profile、配置根目录、运行时与统一显示名。角色、权限、启停、工作目录及会话绑定归当前项目。角色名称由项目自行定义，可留空；工作分工与流程在 AGENTS.md 中约定，工具授权由项目权限页单独保存。

“添加成员”只需选择宿主和自动发现的 profile，第二步直接加入当前项目。在“角色”页定义本项目角色，再通过成员卡的角色按钮选择；权限到“项目权限”页配置，可多选成员及角色。新加入另一个项目时角色为空、权限为空；同一项目重复加入保留既有项目角色。成员卡仅展示已加入本项目的成员，停用成员保留在本项目卡片中。

`PATCH /projects/{id}/members/{profile}/role` 仅管理员可用，接受 `{role: "项目角色"}`；单行文本最多 200 字符。保存同一事务内更新 role 和 role_id，并写入项目配置审计；响应返回实际 role_id。当前项目已有同名角色时关联该实体，空字符串清空关联，兼容自由文本保留文本且 role_id 为 NULL。成员直接授权继续保留，角色授权立即随关联变更。删除角色后历史文本保留，同名重建须显式分配成员；旧数据回填仅迁移时执行一次。`GET /members?project={id}&active_only=true&role={角色}` 精确筛选本项目启用队友；role 省略返回所有启用队友，空字符串筛选未设角色。Bot 使用 `group_list_members(role="本项目角色")` 查询后选定具体 profile，用于 @ 或任务 `next_bot`。

## 项目权限

项目详情的“项目权限”页签按权限列行，每行可多选成员和角色，统一点击“保存权限”生效。需求权限按 `req.create` 创建、`req.update` 更新、`req.resume` 恢复、`req.complete` 关闭、`req.cancel` 撤回排列；任务权限按 `task.create` 创建、`task.update` 更新、`task.resume` 恢复、`task.complete` 关闭、`task.cancel` 撤回排列。

授权按项目/profile 保存；负责人也需显式授权，成员停用时暂不生效。初次升级、新建项目的权限均为空，由用户选择后保存。权限每次工具调用时读取，保存后无需重启；首次部署新代码仍需重启引擎和 Hermes 网关。授予权限后，原有状态及任务接手人约束仍有效。

需求扫描处理开放且未归档、拆解状态为 pending 或 decomposing 占用已超时的需求。通过项目就绪和需求门禁后，从本项目 `task.create` 授权的有效成员中按 role_id 升序、profile 字典序确定一人唤醒；已有部分任务仍可继续拆解。无候选时记录 gate_reason，并尝试通知已配置负责人处理授权。每轮读取当前授权并排除停用/删除成员及 user。拆解完成通过 `task_create(..., complete=true)` 显式提交。

`GET /projects/{id}/permissions` 返回权限目录、成员、grants 和 revision；`PUT` 提交完整 grants 与 revision，仅用户可管理，冲突保留页面输入并提示重新加载。关闭配置窗口放弃未保存的选择，切换 tab 保留草稿。每次变更记录到项目配置日志。

撤回任务的 MCP 操作更新任务状态并返回原接手人；调用者需通知原接手人停止该任务。进程硬停由用户管理入口操作。

## 两种目录模式

项目主目录 `root` 始终保留。

| 模式 | default | 其他 bot |
|---|---|---|
| 共用项目主目录 `shared` | 主目录 | 主目录 |
| 独立 worktree `worktree` | 初始使用主目录，可改为独立 worktree | 初始使用独立 worktree，可改为主目录 |

项目基本信息手动选择模式。独立模式填写 worktree 根目录，成员页可显式指定各自目录。修改模式不会删除或重建已登记的目录；项目主目录变更会检查现有登记的 Git 归属。

唤醒前检查实际目录存在。独立模式同时验证仓库归属及 Git worktree 注册信息；错误返回唤醒失败原因，交由现有失败处理流程处理。每次唤醒沿用现有分支/提交，创建或切换任务分支由 bot 根据 AGENTS.md 和任务上下文执行。

## worktree 操作

成员页显示实际目录、分支/detached、提交及脏状态。目录操作仅限管理员。独立模式项目的每位成员（含 `default`）均有“工作区”按钮，弹窗以单选选择主目录或独立 worktree；点击“保存目录模式”后生效。首次创建/接管的确认操作同时保存独立模式。关闭弹窗放弃尚未保存的选择。切回主目录保留已分配的 worktree，后续可切回或单独确认移除。

- **未分配工作区**：弹窗提供“创建工作区”和“使用已有工作区”。选择后输入路径，点击“确认创建”或“确认接管”才执行。关闭或 Escape 放弃输入。
- **创建**：界面固定从主目录当前 `HEAD` 创建 detached worktree；取消初始版本输入。既有 API 的可选 `start_ref` 保留兼容，页面不再传入。
- **接管**：确认已有目录由当前仓库登记，然后保存项目/profile/路径映射。保留其分支、提交和未提交改动。
- **已分配工作区**：显示当前目录与状态；底部提供“移除工作区…”，点击后展示将删除的具体目录，再点击“确认移除工作区”执行。检查工作区干净、当前提交存在分支引用，使用无 force 的 `git worktree remove`，保留 Git 分支。Git 自身继续检查锁定等状态。

成员页按项目缓存已加载的列表，再次进入时先显示缓存、后台刷新；刷新失败保留列表并显示错误。相同项目的重复加载合并，过期响应不能覆盖新结果。启停或目录操作成功后通过 `?profile=...` 只刷新对应成员。后台每次请求复用 Git common-dir 与 worktree 注册表，最多并行检查 4 个成员，移除分支候选列表查询。

目录必须是绝对路径；主目录、其他成员使用的目录、不同仓库和相互嵌套的 worktree 都会被拒绝。运行中的 bot/唤醒任务会阻止目录变更；引擎内目录操作与 spawn 共享锁。历史恢复记录有不确定的执行时，额外核查对应会话的进程。

Git 与 SQLite 分属两套存储。Git 已创建而后续登记失败时保留目录、记录失败及恢复提示，可以核查后接管；再次创建遇到已存在目录会明确提示。引擎不会强制回滚或清除该目录。

## 存储、接口和记录

- `projects.display_name`、`projects.directory_mode`；`name` 继续作为稳定 ID。
- `project_workspaces(project, profile, path)` 保存显式目录映射。
- `project_workspace_modes(project, profile, mode)` 保存项目内成员目录选择；启动时幂等建表，空表保留原默认行为。项目使用 shared 时所有成员使用主目录，已有成员选择与 worktree 分配保留；改回 worktree 后恢复成员选择。删除项目时清理选择记录。
- `project_config_events` 保存操作者、时间、动作和详情；项目更新包含修改前后配置，成员启停保存前后状态，目录操作保存 profile、路径及创建提交等。
- 变更记录仅保留后台日志，项目配置界面不展示记录入口。
- `GET /projects/{id}/workspaces` 返回成员、工作区状态、主目录引用及最近 30 条配置记录。
- `POST /projects/{id}/workspaces/{profile}`：`action=create/adopt/remove`，可传 `path`，创建可传 `start_ref`；`action=set_mode` 配合 `mode=shared/worktree` 保存成员选择，保存前验证目标目录及成员空闲状态，验证失败回滚配置。
- 创建/修改项目继续使用 `/projects` 和 `/projects/{id}`；成员启停使用 `/members/{profile}/active`，必须携带项目 ID。

全局花名册与项目参与资格分开：新 profile 默认未加入任何项目，新项目默认没有启用成员。用户在“成员与目录”明确启用后，该成员才参与当前项目；权限仍需另行授予。升级时一次性将原有隐式启用状态写成显式记录，保留现有停用状态及归档项目的成员配置；之后新增的项目或 profile 均默认未加入。

负责人必须是项目内有效成员才用于协调和异常通知；无有效负责人时相应通知回退为 user。当前向导在确认提交时按已选团队配置入组、角色和授权，空团队创建后需再配置。负责人变更与成员资格分别校验。

归档前检查本项目 pending/in_progress/blocked 任务、queued/running 唤醒及仍存活或退出状态未确认的 bot。发现未结束工作时返回 409，提示用户先处理，并列出任务/唤醒编号；归档状态保持原样。完成和撤回的历史任务、其他项目工作不阻止归档。归档与 spawn 共用锁，检查与保存处于同一数据库写事务；已归档项目不能新增唤醒或启动 bot。取消归档保留原有成员配置。

## 项目配置系统提示词

每次 spawn 根据本次项目 ID 读取当前数据库配置，调用 `wake_system_prompt`，在 WORK/CHAT 协作规则后追加公共项目段。Hermes 通过 `HERMES_EPHEMERAL_SYSTEM_PROMPT` 加载，Codex 通过 developer_instructions 加载。内容包括项目稳定 ID、显示名、描述、负责人、主目录、实际目录模式、工作目录和分配资源；任务工具 project 使用稳定 ID，群聊发送项目由执行上下文填充。工作目录沿用本次唤醒已校验的路径。负责人未配置、已删除或在该项目停用时为 `user`。负责人自身唤醒仍收到自己的 profile，自行协调及升级规则由 WORK/CHAT 提示词规定。

这段内容不包含当前 profile、规则文件来源或任务/话题编号和时间戳。格式与字段顺序固定；配置未变时生成结果一致，配置变化在下次 spawn 更新。它与 AGENTS.md 原生缓存的生效时机独立，保持原有会话标识和历史，Hermes 源码保持原样。

公共提示词和工具说明直接描述成员选择、消息处理与任务参数，省去重复规则来源声明。角色参考保留专业职责，模板启动入口引导查阅文档索引和任务资料。真实唤醒验收通过 `scripts/verify_prompt_rules_live.py` 在隔离项目检查规则令牌、工具调用与收件箱状态，运行方法见 [测试索引](../../scripts/TEST_INDEX.md)。

提示词提供项目主目录和当前工作目录，文档存放规则由项目 `AGENTS.md` 管理。软件项目的 shared/worktree 成员使用“项目主目录”拼接 `reports/` 共享测试报告；源码、需求、设计和技术文档在分配工作区随分支维护，交接记录路径与提交。目录授权与忽略规则见 [文档存放约定](../guides/DOCUMENT-STORAGE.md)。

## 唤醒前的项目规则同步

引擎每次 spawn 前读取主目录 `AGENTS.md`，在独立工作目录维护 `AGENTS.override.md`。因此直接用编辑器修改主目录文件也会在下次唤醒前同步，无需经设置页面保存。共用主目录的 bot 继续由 Hermes 原生读取该目录。主目录和 worktree 已有的 `AGENTS.md` 正文保持原样。

副本只包含规则正文；数据库 `project_rule_copies` 记录来源、项目 ID、内容 SHA-256 和待写入指纹，以支持跨文件/数据库写入中断后的重试。内容未变时保持文件不动。已有非受管理 override、被手动改动的副本、已跟踪或符号链接 override 会保留并阻止本次唤醒。主目录规则缺失、空白、编码错误、过大，以及工作目录中更高优先级的 `.hermes.md/HERMES.md`，也会明确报错。生成文件通过 Git 本地 `info/exclude` 排除，保持 worktree 状态和提交内容不受副本影响。已有个人 override 需要用户处理后才能接管。

Hermes 原生自动发现 override，仍在原项目规则位置拼接，并继续执行原生安全扫描与长度限制。同步成功表示磁盘副本更新；已有会话可能继续使用已缓存的系统提示词，规则随 Hermes 后续新建或自然重建提示词生效。引擎保持会话名、消息历史、WORK/CHAT 提示和刷新机制；Hermes 源码保持原样。

需要新会话读取最新规则时，通过 `/new` 重建相应会话。

测试：`python -B -m unittest scripts.test_project_rules` 使用临时 Git/SQLite。可设置 `HERMES_TEST_SOURCE` 为 Hermes 源码目录、`HERMES_TEST_PYTHON` 为其解释器，增加真实原生规则加载器验证；该验证不调用模型或创建 bot 会话。

引擎代码更新后由用户手动重启，既有 worktree 在随后唤醒时同步。MCP 由宿主重新加载；Hermes 网关持有的 MCP 进程需重启网关。
