# 需求恢复与空唤醒抑制

`engine/requirement_recovery.py` 为扫描、唤醒上下文与队列有效性检查提供共享条件，设计依据见 [需求恢复调度](../design/2026-10-27-requirement-recovery.md)。

## 自动恢复条件

项目已就绪且未归档，需求为 open 且未归档，拆解状态为 pending 或占用已超时的 decomposing，关联任务中没有 blocked。需求字段与来源经过 `requirement_gate.check`。扫描保存门禁失败原因，唤醒与队列复查保持只读。

扫描按角色 ID、profile 顺序选择一名已启用且持有 task.create 权限的成员，兼容角色授权。缺少有效拆解成员时，扫描记录配置原因并唤醒已启用的 Bot 负责人；负责人取得联系管理员补齐授权的协调指令。负责人变更、授权恢复后，旧协调队列项在投递前重新核对。

blocked 子任务暂停自动拆解恢复。恢复需求保持子任务原状态，维护者须明确恢复相关任务后才能继续自动拆解。独立的消息和可执行任务继续按既有调度处理。

## 部分拆解与提示

已有部分任务的待拆或超时需求继续参与恢复。提示携带需求 ID，要求读取 task_list/task_get、复用已有任务、补齐说明和依赖，按实时凭据契约续写，最后显式提交 complete=true。尚在有效占用期或已完成拆解的需求跳过恢复。

空收件箱的任务和需求唤醒明确说明本次调度原因。消息正文超出注入预算时，保留分页上界、任务后缀和有效需求提示，按原有规则补读消息。

## 队列失效检查

`scan:req` 在队列领取后、调用 deliver 前复查当前需求提示、未读消息和可执行任务。三项均为空时，队列项记为 cancelled，detail 为 `No actionable requirement, unread message or eligible task remains`。新的有效需求、合并的未读消息或可执行任务均可保留同一个队列项。此检查只处理 work 类型的 scan:req，其他唤醒来源保持各自规则。

扫描周期为 180 秒，实际间隔包含扫描耗时及会话占用等待。投递后的业务状态变化由任务工具的事务门禁处理。该修复无需数据库迁移或数据修补；更新引擎代码后由管理员手动重启服务。
